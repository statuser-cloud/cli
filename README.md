# Командная строка Statuser

[![npm version](https://img.shields.io/npm/v/statuser.svg)](https://www.npmjs.com/package/statuser)
[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)

Командная строка для [Statuser](https://statuser.cloud): сценарные проверки как код, плановые работы в CI и heartbeat для крон-задач. Работает поверх [публичного API Statuser](https://statuser.cloud/api-reference) с авторизацией по API-ключу.

```bash
npx statuser --help
```

Нужен Node.js 20.19 или новее. Справка и сообщения — на языке системы: русском или английском.

## Команды

- `scenarios test` — прогоняет файл Playwright-теста в песочнице Statuser без сохранения. Возвращает итог, ошибку и ссылки на скриншот, видео и трейс.
- `scenarios deploy` — создаёт и обновляет сценарные серверы проекта по `statuser.json`.
- `maintenance start`, `maintenance end` — открывают и закрывают плановые работы на странице статуса.
- `servers pause`, `servers resume` — приостанавливают и возобновляют проверки. `resume --from` берёт список серверов из вывода `pause --json`.
- `run` — выполняет команду и отправляет heartbeat: успех при коде выхода 0, ошибку при любом другом.
- `api` — произвольный запрос к API с сохранённым ключом, как `gh api`.
- `login`, `logout`, `whoami` — ключ API на этой машине.

## Ключ API

Ключ создаётся в панели: «Настройки → API».

```bash
statuser login                          # спросит ключ и проверит его
statuser login --with-token < key.txt   # из файла или stdin
statuser whoami
```

Ключ сохраняется в `~/.config/statuser/config.json` с доступом только для владельца. В CI передавайте его переменной `STATUSER_API_KEY`, а не флагом: аргументы команды видны в истории и в списке процессов.

## Сценарии как код

Прогнать файл в песочнице Statuser, ничего не сохраняя:

```bash
statuser scenarios test checks/checkout.spec.ts --location msk-1 --env SHOP_PASSWORD='$SHOP_PASSWORD'
```

В ответе — итог, упавший тест, текст ошибки и ссылки на скриншот, видео и трейс. Ссылки действуют час.

Выкатить сценарии проекта по конфигу:

```bash
statuser scenarios deploy --dry-run   # показать план
statuser scenarios deploy
```

Конфиг `statuser.json` в корне репозитория:

```json
{
  "project_id": 100000,
  "scenarios": [
    {
      "name": "Оформление заказа",
      "file": "checks/checkout.spec.ts",
      "interval": 300,
      "timeout": 60,
      "location": "msk-1",
      "env": { "SHOP_PASSWORD": "$SHOP_PASSWORD" }
    }
  ]
}
```

| Поле | Что значит |
|---|---|
| `name` | Имя сервера в Statuser. По нему сценарий узнаётся внутри проекта |
| `id` | Необязательно. Нужен, чтобы переименовать сценарий: без него новое имя заведёт новый сервер |
| `file` | Файл теста. Один файл до 64 КБ, из пакетов доступен `@playwright/test` |
| `interval` | Как часто проверять, секунд: от 60 до 86 400 и не меньше таймаута. По умолчанию 300 |
| `timeout` | Сколько ждать прогон, секунд: 15, 30, 45, 60 или 120. По умолчанию 30 |
| `location` | Откуда проверять: `msk-1`, `spb-1`, `ala-1`, `nyc-1` или `ams-1`. По умолчанию `msk-1` |
| `env` | Переменные окружения теста. Значение `$NAME` берётся из окружения CI |

Как ведёт себя `deploy`:

- Весь конфиг проверяется до первой записи: ошибка в пятом сценарии не оставит первые четыре выкаченными.
- `env` — полный набор переменных: имя, которое убрали из конфига, удаляется и на сервере. Нет поля `env` — переменные на сервере не трогаются. Значения API не возвращает, поэтому заданные переменные отправляются при каждом запуске.
- Один и тот же текст скрипта не может стоять у двух серверов аккаунта — `deploy` скажет об этом до записи.
- Ничего не удаляется. Сценарии проекта, которых нет в конфиге, только показываются в плане.

## Плановые работы и пауза на время деплоя

Плановые работы показываются на странице статуса и рассылаются подписчикам, но алёрты не глушат. Поэтому вокруг деплоя — два шага: окно на странице и пауза проверок.

```bash
statuser maintenance start --page 12 --servers 101,102 \
  --title "Обновление" --description "Обновляем магазин" --for 20m --json > maintenance.json
statuser servers pause --project 100000 --json > paused.json

# … деплой …

statuser servers resume --from paused.json
statuser maintenance end --page 12 "$(jq .id maintenance.json)" --message "Обновление завершено"
```

- `--servers` — id серверов, которые стоят на этой странице статуса. `--all-servers` берёт все серверы страницы.
- `resume --from` возобновляет только то, что поставила на паузу эта процедура: серверы, которые уже стояли на паузе, такими и останутся.
- `maintenance end` без `--message` только переносит время окончания. С `--message` в таймлайне работ появляется запись, и подписчики получают уведомление. Повторный `end` дату не сдвигает.

## Heartbeat

```bash
STATUSER_HEARTBEAT_TOKEN=… statuser run -- ./backup.sh
```

Команда завершилась с кодом 0 — Statuser получает сигнал «работает», с другим кодом — «ошибка». Код выхода `run` — код самой команды: если сигнал не дошёл из-за сети, успешный бэкап не превратится в упавший.

Для `run` нужен только токен heartbeat из карточки сервера, API-ключ на машине с кроном не нужен. Передавайте токен переменной, а не флагом `--heartbeat`: аргументы видны в списке процессов всё время, пока идёт команда.

Пока не пришёл первый сигнал, Statuser не знает, что задача запущена, и пропуски не считает. Интервал и допустимую задержку heartbeat-сервера задайте с запасом на самую долгую задачу.

Разовый сигнал без команды:

```bash
statuser heartbeat ping "$TOKEN"
statuser heartbeat ping "$TOKEN" --fail
```

## Остальные команды

```bash
statuser servers list --project 100000 --protocol http
statuser servers get 101
statuser api /v1/incidents -F limit=5
statuser api /v1/servers/101 -X PATCH -F check_interval=120
```

У `statuser api` поля из `-F` для GET и DELETE уходят в query, для остальных методов — в тело запроса. `-F` разбирает значение как JSON (`-F on=true` — логическое значение), `-f` всегда передаёт строку. Тело целиком — `--input file.json` или `--input -` из stdin.

У любой команды `--json` печатает машиночитаемый ответ, `--debug` — запросы в stderr (ключ и токены скрыты).

## Коды выхода

| Код | Когда |
|---|---|
| 0 | Успех |
| 1 | Ошибка API или сети, сбой песочницы сценариев |
| 2 | Неверные аргументы или конфиг |
| 3 | Нет ключа или ключ не принят |
| 4 | Сценарий не прошёл (`scenarios test`) |
